# Logging & Observability Guide

This document describes the logging infrastructure for the Boxing Simulation project.

## Overview

The project uses [`logrus`](https://github.com/sirupsen/logrus), a popular structured logging library for Go, wrapped in a simple `Logger` interface that adds component identification to all log entries. All logs include contextual information to enable effective debugging and monitoring.

## Implementation

The logger is implemented in [`internal/platform/logger/logger.go`](../internal/platform/logger/logger.go) as a thin wrapper around logrus that:
- Automatically adds a `component` field for traceability
- Provides a consistent API across the codebase
- Defaults to text output (can be switched to JSON for production)

## Logger API

### Basic Usage

```go
import "github.com/mormm/boxing/internal/platform/logger"

lg := logger.New("component_name")

// Info level - normal operational messages
lg.Info("User registered successfully", "username", user.Username, "user_id", user.ID)

// Error level - error conditions
lg.Error("Failed to process request", "error", err.Error(), "request_id", reqID)

// Warn level - warning conditions  
lg.Warn("Rate limit approaching", "current", currentRate, "limit", maxRate)

// Debug level - detailed debugging information
lg.Debug("Processing event", "event_id", eventID, "boxer_id", boxerID)
```

### Key-Value Pair Format

All logger methods support key-value pairs after the message:
- Message first (without format specifiers like `%s`)
- Followed by an even number of arguments as key-value pairs
- Keys must be strings, values can be any type (int, string, float64, etc.)

**Correct:**
```go
lg.Info("Fight booked", "fight_id", 123, "boxer1", "Alice", "boxer2", "Bob")
// Output: time="2026-10-12 10:00:00" level=info msg="Fight booked" component="component_name" fight_id=123 boxer1="Alice" boxer2="Bob"
```

**Incorrect:**
```go
lg.Info("Fight %d booked", 123)  // Don't use printf-style formatting
```

### Setting Log Level

```go
// Set globally for a logger instance
lg.SetLevel("debug")  // Options: "debug", "info", "warn", "error"
```

## Request ID Correlation (API Requests)

Every HTTP request receives a unique `X-Request-ID` header automatically generated by the middleware. Use this to trace requests across handlers and services:

### In Handlers

```go
import "github.com/mormm/boxing/internal/platform/middleware"

func (h *Handler) HandleRequest(w http.ResponseWriter, r *http.Request) {
    requestID := middleware.RequestIDFromRequest(r)
    
    h.lg.Info("Processing boxer request", 
        "request_id", requestID,
        "boxer_id", boxerID,
        "action", "update")
    
    // Process request...
}
```

### Request ID Propagation

The `X-Request-ID` header is:
1. Generated by `RequestIDMiddleware` if not present
2. Added to response headers for client visibility
3. Available via context in all downstream code

## Worker Event Correlation

Worker logs include event IDs for tracking scheduled events:

```go
// In worker loop
for _, event := range events {
    lg.Debug("Processing event", 
        "event_id", event.ID,
        "event_type", event.EventType,
        "boxer_id", event.BoxerID)
    
    if err := processor.Process(event); err != nil {
        lg.Error("Failed to process event",
            "event_id", event.ID,
            "error", err.Error())
    }
}
```

## Standardized Log Fields

Use these fields consistently for better log analysis:

| Field | Type | Description | Example |
|-------|------|-------------|---------|
| `request_id` | string | HTTP request UUID | `a1b2c3d4-e5f6...` |
| `event_id` | int | Scheduled event ID | `42` |
| `boxer_id` | int | Boxer entity ID | `123` |
| `fight_id` | int | Fight entity ID | `456` |
| `user_id` | int | Authenticated user ID | `789` |
| `training_session_id` | int | Training session ID | `101` |
| `error` | string | Error message | `connection refused` |
| `duration_ms` | int | Operation duration | `150` |

## Log Levels

### DEBUG
Detailed information for troubleshooting. Should not be enabled in production unless debugging specific issues.

```go
lg.Debug("Database query executed", "query", q, "rows_affected", n)
```

### INFO
Normal operational messages. User actions, state changes, successful operations.

```go
lg.Info("Training session scheduled", "boxer_id", id, "training_type", type.Name)
```

### WARN
Potential issues that don't prevent operation. Degraded functionality, rate limits, retries.

```go
lg.Warn("Redis connection slow", "latency_ms", latency, "threshold_ms", threshold)
```

### ERROR
Error conditions that prevent successful operation. Failed requests, database errors, crashes.

```go
lg.Error("Failed to book fight", "boxer1_id", b1ID, "error", err.Error())
```

## Security & Sensitive Data

### NEVER Log

- Passwords (plain text or hashed)
- JWT tokens or API keys
- Database credentials
- Personal identifiable information (PII) beyond what's necessary for audit

### OK to Log

- Usernames (for audit trail)
- User IDs
- Email addresses (in registration/login logs)
- Error messages (that don't expose secrets)
- Request/response metadata (not body content with sensitive data)

```go
    h.lg.Info("Book fight request received",

        h.lg.Error("Failed to book fight",

            "error", err.Error())

        "boxer2_id", boxer2ID)
    
    // ... validation logic ...
    
    s.lg.Info("Creating fight record",
        "request_id", requestID,
        "fight_id", newFight.ID)
    
    return nil
}
```

## Production Configuration

For production environments, you can switch to JSON output format for better log aggregation:

```go
// In logger.New() or after creation
l.SetFormatter(&logrus.JSONFormatter{
    TimestampFormat: time.RFC3339Nano,
})
```

This produces structured JSON logs compatible with:
- ELK Stack (Elasticsearch, Logstash, Kibana)
- CloudWatch Logs Insights
- Datadog
- Splunk

## Troubleshooting

### Logs Not Appearing

Check that the log level is set appropriately. By default, only INFO and above are shown:

```go
lg.SetLevel("debug")  // Enable DEBUG logs during troubleshooting
```

### Finding Request Logs

Filter logs by request ID (JSON output):
```bash
grep '"request_id":"a1b2c3d4"' server.log
```

Or with text output:
```bash
grep 'request_id="a1b2c3d4"' server.log
```

### Tracking Event Processing

Worker logs include event_id for all scheduled event operations:

```bash
grep 'event_id="42"' worker.log
```

### Filter by Log Level (text output)

```bash
# Only ERROR logs
grep 'level=error' server.log

# WARN and above
grep -E 'level=(warn|error)' server.log
```

### Filter by Component

```bash
# All auth component logs
grep 'component="auth"' server.log
```
